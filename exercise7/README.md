# Exercise 7 — Linux VMs and the SSH key

Two VMs and the one key pair they share.

## What you build

- `web1` — private, no public IP, Apache installed by cloud-init
- `jump` — public IP, no Apache, the host you SSH into
- One RSA key pair, written to `<prefix>-ssh-key.pem` in this directory

## Run it

```bash
cd exercise7
terraform init
terraform apply
```

Terraform returns before the VMs finish booting. Allow about a minute for
cloud-init to install Apache.

## Check it

```bash
terraform output ssh_commands
ssh -i ./<prefix>-ssh-key.pem azureuser@<jump public ip>
```

Then from the jump host, across the peering from exercise5:

```bash
ping 10.20.1.4
curl http://10.20.1.4
```

To reach the private VM directly from your laptop:

```bash
K=$PWD/<prefix>-ssh-key.pem
ssh -i $K -o ProxyCommand="ssh -i $K -W %h:%p azureuser@<jump public ip>" azureuser@10.20.1.4
```

Use `ProxyCommand`, not `-J`. `ssh` does **not** pass `-i` to the jump hop, so
`-J` offers your default `~/.ssh` keys there and is refused. Running
`ssh-add ./<prefix>-ssh-key.pem` first makes plain `-J` work too.

## Worth knowing

**The key is generated by Terraform**, not `ssh-keygen`, in this module's
`key.tf`. It is written to disk at mode `0600` and `.gitignore` excludes `*.pem`.
It is also stored in `terraform.tfstate` in plaintext, so treat that file as a
secret. Fine for a lab, not for anything real.

**This module is called once**, unlike every other module here, and loops over
the VM map internally. That is deliberate: one key must be shared by all VMs,
and a module called per instance would generate one key each.

**`custom_data` is applied only at creation.** Editing the page, or setting
`lb_public_ip` below, changes cloud-init and therefore **replaces** the VM.

**There is a deliberate circular dependency here.** The demo page wants to show
the load balancer's address, but the load balancer in exercise8 needs these VMs'
NICs first. So: apply this now with `lb_public_ip` unset, do exercise8, then put
the address into `lb_public_ip` here and re-apply. A single all-in-one root can
resolve this automatically; separate roots cannot, which is a real tradeoff of
splitting state.
